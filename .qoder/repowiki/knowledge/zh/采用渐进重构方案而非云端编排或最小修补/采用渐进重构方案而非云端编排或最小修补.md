# 采用渐进重构方案而非云端编排或最小修补

_来源：1bc7587 → 5c81ef8 提交周期内记录的编码计划——内容为规划时意图，实现可能滞后或有出入。_

**状态：** accepted

## 背景
项目面临产物协议缺陷、音频合成闭环缺失、编排不一致等多维度问题，需要在三种路径中选择：最小修补当前 Pi 架构、渐进重构、或迁移到 Trigger.dev + OpenAI Agents SDK 的云端管线。

## 决策驱动
- 本地优先 PRD 约束
- P0 风险优先级（产物协议 > 音频闭环 > 编排）
- 可回滚性
- 开发成本与时间

## 备选方案
- **方案1：最小修补当前 Pi 架构** _（已否决）_ — 优点：改动范围小（~500 LoC），时间快（3-5天），风险低，数据无需迁移；缺点：只修表层 bug，不解决产物协议和音频闭环，长期维护风险仍在
- **方案2：渐进重构（推荐）** — 优点：按优先级渐进，每步可验证，覆盖全部问题域，职责清晰利于长期维护；缺点：需要 4-6 周，涉及多模块重构
- **方案3：Cloud Pipeline（Trigger.dev + Agents SDK）** _（已否决）_ — 优点：完全解决编排问题，分布式 worker 协作好；缺点：与本地优先 PRD 冲突，beta 依赖风险高，SQLite→Postgres 数据迁移困难，部署模式改变导致回滚困难

## 决策
选择方案2渐进重构，建立 R0-R7 七个 Track 逐步实施，通过 PIPELINE_V2 feature flag 控制新旧引擎切换，确保每步可回滚。

## 影响
需要 4-6 周完成全部重构，但每个 Track 独立可验证；旧项目保持只读兼容；SQLite/LocalFS 保留至商业化阶段；Pi Agent 在 R4 观察期后于 R6 清退。
